# ADR 0001: การบริหารจัดการกิจกรรมจากส่วนกลางด้วยสิทธิ์ Super Admin

## สถานะ (Status)
Proposed (กำลังตัดสินใจใน Grilling Session)

## บริบท (Context)
ปัจจุบันระบบ KMUTT OpenHouse แบ่งแยกผู้ดูแลระบบออกเป็นบัญชีแยกตามคณะและหน่วยงาน (เช่น `KM_FEN`, `KM_sit`, `KM_fibo` รวมกว่า 40+ บัญชี) โดยแต่ละบัญชีมีสิทธิ์เฉพาะกิจกรรมที่ตนเองเป็นเจ้าของ (`Activities.ownerId = req.user.id`)

ในทางปฏิบัติ การรวบรวมและบันทึกข้อมูลกิจกรรมมีผู้ประสานงานส่วนกลางเพียงคนเดียวเป็นผู้รับผิดชอบ ทำให้ต้องล็อกอิน-ล็อกเอาท์สลับบัญชีไปมาตามแต่ละคณะเพื่อสร้างกิจกรรม ส่งผลให้เกิดความล่าช้าและเกิดความผิดพลาดในการจัดการข้อมูล (Operational Bottleneck)

นอกจากนี้ เมื่อกิจกรรมถูกสร้างขึ้น จะต้องเชื่อมโยงไปยังเจ้าหน้าที่หน้างาน (`Staffs`) ของคณะนั้น ๆ ผ่านตาราง `StaffMapping` โดยอัตโนมัติ เพื่อให้ Staff ประจำคณะสามารถสแกน e-Stamp ได้ทันที

## การตัดสินใจ (Decision)
1. **เพิ่มระดับสิทธิ์ `role` ในโมเดล `Admins`**:
   - เพิ่มฟิลด์ `role AdminRole @default(ADMIN)` โดยมีค่า `SUPER_ADMIN` และ `ADMIN`
   - กำหนดให้บัญชี `KM_admin` เป็น `SUPER_ADMIN`
2. **การกำหนดเจ้าของกิจกรรมแบบ Smart Auto-Select (Hybrid)**:
   - ในหน้าสร้างกิจกรรม ([`AddActivityPage.tsx`](./src/views/pages/_km/activities/AddActivityPage.tsx)) เมื่อ Super Admin เข้ามาสร้างกิจกรรม ระบบจะแสดงช่องเลือก "เจ้าของกิจกรรม (Owner)"
   - เมื่อเลือกภาควิชา/สาขาวิชา (Department) ระบบจะวิเคราะห์หา Admin คณะที่เกี่ยวข้องและเลือกให้อัตโนมัติเป็นค่าเริ่มต้น โดย Super Admin ยังสามารถเปลี่ยนมือเองได้
3. **การเข้าถึงและการแสดงผลแบบรวมศูนย์ (Global Dashboard with Filters)**:
   - ในหน้า [`/_km/dashboard`](./src/views/pages/_km/KMDashboard.tsx) บัญชี Super Admin จะมองเห็นกิจกรรมทั้งหมดของทุกคณะ พร้อมแถบตัวกรอง (Filter by Faculty/Owner)
   - Super Admin สามารถแก้ไขหรือลบกิจกรรมของคณะใดก็ได้
4. **การทำงานร่วมกับ Staff Auto-Assign**:
   - เมื่อสร้างกิจกรรม ระบบจะอ้างอิง `ownerId` ที่ถูกเลือก (ไม่ใช่ `req.user.id` ของ Super Admin) เพื่อทำ auto-assign ให้กับ Staff ของคณะเจ้าของกิจกรรมทันที

## ผลกระทบ (Consequences)
- **เชิงบวก (Positive)**:
  - ผู้ประสานงานส่วนกลางล็อกอินเพียงบัญชีเดียว (`KM_admin`) ก็สามารถจัดการกิจกรรมได้ทั้งมหาวิทยาลัย
  - ลดภาระงานและลดความเสี่ยงที่ Staff หน้างานจะไม่มีกิจกรรมให้สแกน
  - Admin ประจำคณะเดิมยังคงล็อกอินเข้ามาดูและจัดการเฉพาะของตัวเองได้ตามปกติ โดยไม่กระทบสิทธิ์เดิม
- **สิ่งที่ต้องระมัดระวัง (Negative / Trade-offs)**:
  - ต้องปรับปรุง API Guard และ Database Query ให้ตรวจสอบ `role === 'SUPER_ADMIN'` ก่อนคัดกรองข้อมูล
  - ต้องจัดการความสัมพันธ์ในการจับคู่ระหว่าง Department และ Admin คณะ ให้ถูกต้องแม่นยำ
